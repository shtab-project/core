# Shtab — план

> Живой документ. Сюда попадает только то, о чём договорились.
> ✅ — решено · 💡 — предложено, ещё обсудить · ❓ — открытый вопрос

## Видение

Shtab — своя рабочая экосистема организации на своём сервере: **ядро** с аккаунтами,
проектами и маркетом плагинов, а всё полезное (задачи, заметки, мессенджер, мониторинг,
интеграции) — **плагины**, которые ставятся в проект из маркета.
ИИ-помощник (ChatGPT Plus / Claude Pro) работает с системой через MCP.

### Ядро

- **Организация.** ✅ При первом запуске Shtab создаётся организация (задаётся название).
  В ней: задачи и заметки организации, проекты, личные пространства пользователей.
  ✅ Одна установка Shtab = одна организация (без нескольких организаций на сервере).
- **Аккаунты.** Регистрация закрыта; аккаунты живут в Authentik. Ядро хранит
  профиль пользователя, полученный при входе.
  ✅ Роли уровня системы:
  - **администратор** — управляет пользователями и маркетом;
  - **доверенное лицо** — может редактировать общие заметки организации;
  - **пользователь** — всё остальное.
  ✅ Доверенных назначает администратор; сам администратор — доверенный по умолчанию.
  ✅ Аккаунт выдаёт только админ — ссылкой-приглашением, пароль человек задаёт сам
  (Authentik умеет из коробки). В проект зовут уже существующих пользователей.
  Позже, возможно, — настройка, чтобы приглашение в проект по email создавало аккаунт.
- **Личное пространство.** ✅ У каждого пользователя — своё личное пространство со
  своими задачами и заметками (это не проект: без участников и приглашений).
  ✅ В нём доступны все плагины, поставленные админом; пользоваться ими или нет — его дело.
- **Проекты.** Создатель — владелец. Новый проект пустой: в нём только участники.
- 💡 Для плагинов всё это — одно понятие **«пространство»** (`space_id`) трёх типов:

  | Тип | Кто видит | Кто редактирует |
  |---|---|---|
  | `org` — организация | все пользователи | доверенные лица |
  | `project` — проект | участники проекта | участники проекта |
  | `personal` — личное | владелец | владелец |

  Плагин не разбирается в правилах сам — спрашивает у ядра «может ли X читать / писать
  в пространстве S».
- **Приглашения.** Владелец приглашает по id, email или иначе → пользователь
  принимает → становится участником.
- **Маркет.** Каталог плагинов. ✅ Ставит плагины в систему только администратор.
  ✅ Пока заглушка: список моих плагинов из GitHub; «Установить» = скачать с GitHub
  и развернуть на сервере.
  💡 Готовый Docker-образ собирает GitHub Actions и кладёт в GitHub Container Registry
  (ghcr.io), маркет берёт `manifest.yaml` из репозитория и скачивает образ — собирать
  на сервере не нужно.
  💡 Развёртыванием занимается отдельный маленький сервис-установщик с доступом к Docker,
  а не само ядро (доступ к Docker = права root на сервере).
  ✅ Включает плагин в проекте владелец проекта — из поставленных админом.
  ✅ Все участники проекта видят все включённые в нём плагины; ограничений участника
  по плагинам нет (тонкие права — внутри самих плагинов).
  Плагин — один экземпляр на всю систему, обслуживает все проекты (не дублируется
  на пользователя).

### Контракт плагина

**Состав плагина:**
```
plugin/
├── manifest.yaml   — имя, версия, нужные права к API ядра, подписки на события,
│                     место в интерфейсе, инструменты для ИИ
├── backend         — любой язык (наши — на FastAPI), своя БД
└── frontend        — один ES-модуль с Web Component (<shtab-tasks project="…">)
```

**Каналы связи:**

| Канал | Направление | Пример |
|---|---|---|
| REST API ядра | плагин → ядро | участники проекта; может ли user X делать Y в проекте P |
| Вебхуки | ядро → плагин | плагин включён / выключен в проекте; участник добавлен / удалён; проект удалён |
| Запросы пользователя | браузер → шлюз → плагин | список задач, создать задачу |

💡 Плагины открываются по путям через шлюз ядра (`shtab.<домен>/plugins/<id>/…`),
а не на своих поддоменах — хватает одного домена и одного сертификата.

**Ядро даёт плагинам:**
- проверенного пользователя в каждом запросе;
- проверку прав и список участников проекта;
- события жизненного цикла (вебхуки);
- место в интерфейсе проекта (вкладка / пункт меню);
- `shtab-ui.css` — общие стили и токены (выгружаются из темы фронта ядра);
- `shtab-sdk.js` — `shtab.user`, `shtab.project`, `shtab.api()`, `shtab.navigate()`;
- публикацию инструментов плагина в общий MCP;
- *позже* — уведомления (`shtab.notify()`).

**Главное правило:** плагин не трогает таблицы ядра и других плагинов — только API.

💡 Предложено, обсудить детали:
- Шлюз проверяет сессию и передаёт плагину подписанный токен (JWT) с пользователем;
  плагин проверяет подпись ключом ядра.
- Членство в проекте плагин кэширует; кэш сбрасывается вебхуком «участник удалён».
- Вебхуки ядро отправляет через очередь (taskiq) с повторами до успешного ответа.
- Сторонние плагины (в будущем) — в iframe с sandbox, свои — встраиваются напрямую.

### Плагин «Задачи»

- ✅ Задачи есть на всех трёх уровнях: организации, проекта, личные.
- ✅ Задачи организации может создавать любой пользователь (в отличие от заметок
  организации, где редактируют только доверенные).
- ✅ Два режима видимости внутри проекта:
  - **проектная** — видят все участники проекта;
  - **закрытая** — видят создатель и приглашённые в задачу.
- ✅ Задача «только для себя» — закрытая без приглашённых.
- ✅ Колонки канбана пока фиксированные (настройка колонок по проектам — позже).
  💡 К выполнению → В работе → На проверке → Готово.
- ❓ Поля задачи. 💡 Название, описание, исполнители, срок, приоритет, теги.
- Позже: упоминания `@имя`, уведомления.

### Плагин «Заметки»

- ✅ Текст — Markdown, хранится в PostgreSQL (нужны быстрый поиск и совместная правка).
- 💡 Поиск: полнотекстовый поиск Postgres с русской морфологией + `pg_trgm` (опечатки).
- 💡 Совместная правка: Yjs (CRDT), на бэкенде — `pycrdt`.
- 💡 История версий — таблица ревизий; экспорт в `.md` для бэкапа и Obsidian.
- 💡 Идеи из SilverBullet: ссылки `[[…]]`, теги `#…`, запросы.
- ✅ Три уровня:
  - **организации** — общие для всех: просмотр у всех, редактирование только у доверенных лиц;
  - **проекта** — у каждого проекта свои;
  - **личные** — в личном пространстве.
- 💡 Внутри проекта — как у задач: проектные (все участники) и закрытые (автор + приглашённые).

## Authentik: что настроить

Разовая ручная настройка при развёртывании:

1. **Поднять Authentik** в общем docker-compose (server + worker); база — отдельная БД
   в нашем PostgreSQL.
2. **Первичная настройка** — создать учётку администратора Authentik
   (`/if/flow/initial-setup/`).
3. **Закрыть регистрацию** — не включать публичный поток регистрации.
4. **Поток регистрации по приглашению** — enrollment flow со стадией Invitation:
   человек открывает ссылку → задаёт логин и пароль → аккаунт создан.
5. **OIDC-приложение «Shtab»** — OAuth2/OIDC-провайдер для ядра: client id / secret,
   redirect URI ядра. Через него идёт вход в веб-интерфейс.
6. **Proxy-провайдер + outpost для Traefik** (forward-auth) — для того, что само не умеет
   OIDC: сторонние плагины, закрытые dev-сайты.
7. *Позже:* SMTP — чтобы Authentik отправлял письма (сброс пароля, приглашения).

Дальше — автоматически, без захода в админку Authentik:

- 💡 Админ нажимает «Пригласить» в интерфейсе Shtab → ядро через API Authentik создаёт
  приглашение и показывает ссылку.
- 💡 Роли (администратор, доверенное лицо) и проекты хранятся в ядре, не в группах Authentik:
  Authentik отвечает только за «кто ты».
- 💡 Первый вошедший пользователь при первом запуске Shtab становится администратором
  (мастер настройки: название организации + администратор).

**⚠️ Риск с MCP.** ChatGPT и Claude подключаются к MCP через OAuth и ожидают, что сервер
авторизации умеет регистрировать клиентов сам (Dynamic Client Registration / Client ID
Metadata Documents). Authentik этого пока не поддерживает.
- 💡 Решение: MCP-шлюз ядра сам выступает OAuth-сервером для ИИ-клиентов, а вход
  пользователя перенаправляет в Authentik (схема «OAuth-прокси»).
- ❓ Проверить: принимают ли коннекторы заданный вручную client ID — тогда прокси не нужен.
